# Changelog

The public history of Viper PQ Chain starts with its first public release. The code
had three private predecessors — `viper-pq-1` (2026-04 → 2026-05), `viper-research-1`
(2026-05 → 2026-08) and an internal lab — whose day-by-day changelog stays in the
private repository; what they decided is in DECISIONS.md, what they left open is in
KNOWN-ISSUES.md.

## [Unreleased] — public release preparation (opened 2026-08-24)

### 0.2.3 — nodes run by others actually sync; signed network files (2026-11-16)

- **Fix: a node outside the operator's cluster could not catch up.** On a block-height gap (or a missing parent) the node asked the block's *publisher* for the missing range — the validator, which sits behind the public seed and cannot be dialled — so every request failed and a fresh node stayed at height 0. The swarm now surfaces the gossip `propagation_source` as `forwarded_by`; block-fetch goes to that connected peer and falls back to the publisher. Identity checks (SPEC-P2P-002 §4.4) still use the publisher only.
- **Security: per-node ML-KEM salt.** `join-testnet.sh` (and the container recipe in the onboarding guide) now generate `kem_seed_salt_hex` as well as the libp2p salt; without it a node's ML-KEM identity key was derivable from its public `node_id`.
- **Signed network files.** Each release carries `viper-testnet-*-genesis.json` and `viper-testnet-*-full.json` inside the signed `SHA256SUMS`; `join-testnet.sh` takes them from the release instead of a branch.
- `join-testnet.sh`: audit log under the node directory (no more `/var/log/pqchain` permission error for a normal user); with `--systemd` the default directory is `/var/lib/viper-testnet` (the service user cannot enter `/root`).
- The startup banner describes the test network as it is (one operator, no audit, no token, may be reset).
- Ceremony: the notary write routes are off on every role.
- Public status page at <https://pqchain.agwswebconsulting.it/> (`site/`): height, block time, nodes connected to the seed, latest blocks, algorithms, how to join.
- Contributions: pull requests are now reviewed and merged by the maintainer; commits must be signed off under the new [CLA](CLA.md), enforced by the `contributor-terms` check.
- Docs: aligned with viper-testnet-3 (current network, endpoints, numbers, SDK status); notary references removed.
- Security: `aws-smithy-json` 0.62.5 → 0.62.7 (GHSA-8ffr-xgwf-xj56, uncontrolled recursion). Only reachable through the optional `s3-upload` feature, which release binaries do not enable.

### 0.2.2 — release binaries that run on Ubuntu 22.04 / Debian 12 (2026-11-16)

- The 0.2.1 binaries were built on the current `ubuntu-latest` image and required glibc 2.38 and a GCC 13+ libstdc++: they did not start on Ubuntu 22.04 or Debian 12. The binary job now builds on `ubuntu-22.04` and refuses a binary that needs more than glibc 2.35; `join-testnet.sh` says so upfront on an older system. Container images were not affected.

### 0.2.1 — dependency security updates (2026-11-16)

- **Dependencies:** `quinn-proto` 0.11.19 / `quinn-udp` 0.5.16 (six advisories on the QUIC transport, among them remote panics), `rustls` 0.23.46 (among others RUSTSEC-2026-0349, an unauthenticated ServerHello could downgrade later connections to classical key exchange), `rustls-webpki`, `webpki-roots`, `libp2p-gossipsub` 0.49.5, `tokio` 1.54.1, `zstd`, `cryptoki`, `ctutils`, `aws-lc-rs`. `cargo deny check` is green; the advisories with no fix on the libp2p 0.56 line are listed with their reachability in `deny.toml` and KNOWN-ISSUES R-17.
- **CI / release:** GitHub-hosted runners build RocksDB 8.10 with `CXXFLAGS=-include cstdint` (newer GCC). The `v0.2.0` tag has container images but no binaries and no GitHub Release (the binary job failed on exactly this); use `v0.2.1`.

### 0.2.0 — `viper-testnet-3`, QUIC on the wire (2026-11-16)

- **QUIC is now actually the primary transport.** ADR-041 said "QUIC primary, TCP/TLS 1.3 fallback" and the swarm was built with both transports, but `listen_addr_for_role` only ever produced a `/tcp/` multiaddr and `quic_enabled` / `tcp_tls_fallback` were read from `node.json` and then ignored — no node ever listened on UDP. The swarm now listens on `/ip4|ip6/<addr>/udp/<port>/quic-v1` when `quic_enabled` and on `/tcp/<port>` when `tcp_tls_fallback` (both on by default, same port number), and refuses a config with both off. Both handshakes negotiate X25519MLKEM768 with `hybrid-kem-tls`. New test `two_swarms_connect_and_gossip_over_quic_only` (TCP switched off) next to the existing TCP one; end-to-end, a validator and a full node with TCP disabled sync over QUIC alone.
- **`libp2p.external_addrs`** (`node.json`, `P2pConfig::external_addrs`): public multiaddrs a node advertises through Identify/Kademlia — needed by a seed that listens on a pod or NAT address.
- **Ceremony:** `quic_enabled: true` in every role; bootstrap lists carry each peer twice, QUIC first and TCP second. Reference configs (`configs/roles/*.json`) and the Ansible defaults switch QUIC on.
- **Chart 0.6.0:** UDP `p2p-quic` port on every chain container and headless Service; `chainNode.<role>.p2p.expose` publishes ordinal 0 of a role as a public seed (QUIC + TCP on one `LoadBalancer`/`NodePort` Service, `externalTrafficPolicy: Local`); `chainNode.<role>.config.secretRef` mounts `node.json` from a Secret; `extraObjects`.
- **`viper-testnet-3`** — the public test network (genesis in `genesis/viper-testnet-3/`, 6 s blocks, one validator, one public seed). `scripts/join-testnet.sh` installs a full node in one command (release binary checked against `SHA256SUMS`, genesis checked against its digest, ready `full.json`). `viper-testnet-2` retired 2026-09-23.
- **`tools/viper-ricordi`** — ML-DSA-65 key generation, signing and verification plus an `attestation_create` transaction builder: a worked example of anchoring an attestation on the chain.

### Security

- **`pqcd ceremony` put every validator's signing seed in every role's `node.json`.** The comment said it was for distributed signing; in practice the sentry, full, rpc, archive and bootnode configs — rendered by the chart into ConfigMaps — each carried `devnet.validators[].commit_seed_hex`, so anyone able to read one of them could sign as the validator. Only the validator role gets the seeds now (test `only_the_validator_node_json_carries_signing_seeds`), and its `node.json` belongs in a Secret (`config.secretRef`). Networks created with an earlier ceremony should treat the validator seed as exposed to whoever could read those ConfigMaps.
- Removed the `deploy-testnet` workflow: it targeted `viper-testnet-2` through a self-hosted runner that no longer exists.

### Changed

- **`crates/pqc-light-client`** — new crate: the `SPEC-LIGHT-CLIENT-001` module extracted from `pqc-consensus`, depending on `pqc-crypto` only. `pqc-consensus` re-exports it, existing paths unchanged (ADR-068, TASK-236).
- **`crates/pqc-keystore`** — new crate: the wallet keystore extracted from `pqcd` (`pqcd::wallet` is now a re-export). `viper-archival-sidecar` depends on it directly and no longer links `pqcd` (ADR-068, TASK-236).

- **Node roles in the binary (ADR-069, TASK-240).** `devnet.role` now speaks the chart's vocabulary: `validator`, `sentry`, `full`, `rpc`, `archive`, `bootnode`, plus `single_node`; `producer` and `follower` are read as aliases of `validator` / `full` and never written. `NodeRole` carries the behaviour as predicates (`is_validator`, `keeps_full_history`, `p2p_role`, `serves_public_tx_submission`, …) and every `matches!` on the role in `devnet.rs` / `node.rs` / `p2p.rs` goes through them; `snapshot-prune` now also refuses `archive` nodes; a startup lint reports a validator / bootnode / single node with `api.public_tx_submission` on. `$VIPER_NODE_ID` overrides `node_id` at load (the chart sets it from the pod name, so replicas of one role no longer share a libp2p / ML-KEM identity). `pqcd ceremony` emits one `node.json` per chart role (six) with the role-correct listen field, `api.public_tx_submission` and topology — sentries dial the validator, everything else dials the sentries, PeerIds derived from pod names — and records `_release_name` / `_namespace`. Chart 0.3.0: `VIPER_NODE_ID` from the downward API, a render guard that refuses ceremony values generated for another release or namespace (the `viper-lab-1` cold-start: followers dialling `viper-test-…` while the release was `pqchain`), README role table with the binary column. `configs/roles/<role>.json` reference examples, pinned by `configs_roles_examples_match_their_role`.

- **Pre-genesis gaps (KNOWN-ISSUES §2).** G-01: `pqcd ceremony` now generates a libp2p salt and an ML-KEM salt per role, emits one identity Secret per role (`<release>-pqcd-<role>-identity`, keys `libp2p_seed_salt_hex` / `kem_seed_salt_hex`) referenced by `chainNode.<role>.identitySalts.secretName`, and derives the bootstrap PeerIds with them; pqcd reads the salts from `VIPER_LIBP2P_SEED_SALT_HEX` / `VIPER_KEM_SEED_SALT_HEX` (never from a ConfigMap) — no transport identity is recomputable from the public `node_id` any more; the Ansible template accepts the same two values from a vault. G-02 / TASK-241: `pending_precommits` and `own_precommits_emitted` were never evicted (the comment said they were) and grew by one entry per block for the life of the process — the most plausible cause of the validator OOM on the internal lab; both are now pruned at or below the tip on every insert. G-03 / TASK-239: every deadline in `product_workflows.rs` scales with `PQCD_TEST_TIME_SCALE`.

- **Disk growth on a single-node cluster: WAL cap, follower prune in the chart (0.4.0), `viper-testnet-2` at 2 s blocks (2026-09-11).** The testnet filled 91 % of its node's disk in 17 days — ~1.25 GB a day per chain node at 500 ms blocks, a quarter of it write-ahead logs. `open_rocksdb` now caps the WAL at 256 MiB (`max_total_wal_size`): each follower held 104 WAL files, 6.5 GB, pinned by the quiet `meta`/`checkpoints` column families. `chainNode.<role>.prune` wires TASK-187a on Kubernetes — a `snapshot-prune` initContainer (a failed prune never keeps the node down) and a weekly CronJob that restarts the StatefulSet; the chart refuses it on validator and archive. On the testnet the sentries and the full node keep the last 1 209 600 blocks, the validator keeps everything, and the block time goes from 500 to 2000 ms (TASK-186 option b), about four times less growth.
- **Chart 0.3.1 — `notary.persistence`; upgradable StatefulSets.** The chain StatefulSets' `volumeClaimTemplates` carried the chart-version label, so any chart bump broke `helm upgrade` (immutable field); they now carry selector labels only — existing releases need one `kubectl delete statefulset --cascade=orphan` before the first upgrade to 0.3.1. The notary's evidence-chain index can live on a PersistentVolumeClaim (`Recreate` strategy, `replicas: 1`); off by default. ADR-072 fixes the fee posture of tokenless networks: fees stay, operator services are funded at genesis.
- **`viper-testnet-2` genesis (2026-08-25) — `viper-testnet-1` retired the same day.** The first network could never fund an account after genesis (fees settle from the sender's balance even without token economics; `vault_create` opens accounts empty; transfers are compiled out), so the notary's service account could not exist. `pqcd ceremony --service-account <label>:<pk>` now funds operator services at genesis; `viper-testnet-2` was born with the notary and an operator account, and the public notary runs on it in anonymous mode. Genesis artefact and digest under `genesis/`; the retired `viper-testnet-1` files stay for the record.
- **`viper-testnet-1` genesis (2026-08-25).** Ceremony with one validator, install on the author's cluster (validator, two sentries, one full node, explorer; images `v0.1.2`), `genesis/viper-testnet-1.json` with its SHA-256 and the two sentry bootstrap multiaddrs published; explorer and read API on `https://pqchain.agwswebconsulting.it`, P2P on `boot1.pqchain.agwswebconsulting.it:26656`. ### Fixed

- `pqc-light-client` / `pqc-keystore`: the extracted crates opt into the workspace lints (their origins, `pqc-consensus` and `pqcd::wallet`, never did), so `cargo clippy -D warnings` surfaced 17 `indexing_slicing` / `expect_used` sites. All fixed without behaviour change: committee selection sorts and walks the validator set through iterators instead of raw indexing, CBOR signature pairs are destructured with `<[Value; 2]>::try_from`, BIP39 seed derivation uses the infallible `pbkdf2_hmac_array`, the HMAC-SHAKE key padding zips instead of slicing; the one unreachable `expect` (ciborium writing into a `Vec`) lives in a single documented helper. Test modules carry the workspace's usual `#![allow(clippy::unwrap_used, clippy::expect_used, clippy::indexing_slicing)]`. Direct `hmac` dependency dropped from `pqc-keystore`.
- `pqcd` doctest `cold_storage::upload_to_s3`: the `cargo build --features s3-upload` hint in the doc comment was an indented block, which rustdoc compiles as Rust; it only surfaced under `--all-features` (the CI test job never ran). Now a `text` fence.
- `crates/pqcd/tests/malicious_node.rs` — `invalid_parent_hash_blocks_get_rejected`: under `attack-modes` the attacker (validator-1) corrupts its own tip, so its own `append_block_trusted` rejects the block it built (`PARENT_HASH_MISMATCH`) and its consensus loop ends with an error; the test then failed on `shutdown()` although the property under test (honest majority keeps advancing) had passed. The attacker's join error is now reported, not propagated; the honest nodes must still shut down cleanly. The `malicious_node` binary gets `required-features = ["attack-modes"]`: without the feature no fault is injected and every scenario was vacuously green, which is how TASK-219b saw it pass in April.
- First full `cargo test --workspace --all-features` on record: 935 passed, 8 ignored; the three failures were the two above plus the load-sensitive `external_validator_registers_and_participates_in_quorum` (passes alone, TASK-239).
- `pqcd::tls`: the `tracing` import is now gated on `hybrid-kem-tls`, the only feature that uses it (was the single warning in a clean `cargo check --workspace --all-targets`).
