# Changelog

The public history of Viper PQ Chain starts with its first public release. The code
had three private predecessors — `viper-pq-1` (2026-04 → 2026-05), `viper-research-1`
(2026-05 → 2026-08) and an internal lab — whose day-by-day changelog stays in the
private repository; what they decided is in DECISIONS.md, what they left open is in
KNOWN-ISSUES.md and TASKS.md.

## [Unreleased] — public release preparation (opened 2026-08-24)

### Changed

- **`crates/pqc-light-client`** — new crate: the `SPEC-LIGHT-CLIENT-001` module extracted from `pqc-consensus`, depending on `pqc-crypto` only. `pqc-consensus` re-exports it, existing paths unchanged (ADR-068, TASK-236).
- **`crates/pqc-keystore`** — new crate: the wallet keystore extracted from `pqcd` (`pqcd::wallet` is now a re-export). `viper-archival-sidecar` depends on it directly and no longer links `pqcd` (ADR-068, TASK-236).

- **Node roles in the binary (ADR-069, TASK-240).** `devnet.role` now speaks the chart's vocabulary: `validator`, `sentry`, `full`, `rpc`, `archive`, `bootnode`, plus `single_node`; `producer` and `follower` are read as aliases of `validator` / `full` and never written. `NodeRole` carries the behaviour as predicates (`is_validator`, `keeps_full_history`, `p2p_role`, `serves_public_tx_submission`, …) and every `matches!` on the role in `devnet.rs` / `node.rs` / `p2p.rs` goes through them; `snapshot-prune` now also refuses `archive` nodes; a startup lint reports a validator / bootnode / single node with `api.public_tx_submission` on. `$VIPER_NODE_ID` overrides `node_id` at load (the chart sets it from the pod name, so replicas of one role no longer share a libp2p / ML-KEM identity). `pqcd ceremony` emits one `node.json` per chart role (six) with the role-correct listen field, `api.public_tx_submission` and topology — sentries dial the validator, everything else dials the sentries, PeerIds derived from pod names — and records `_release_name` / `_namespace`. Chart 0.3.0: `VIPER_NODE_ID` from the downward API, a render guard that refuses ceremony values generated for another release or namespace (the `viper-lab-1` cold-start: followers dialling `viper-test-…` while the release was `pqchain`), README role table with the binary column. `configs/roles/<role>.json` reference examples, pinned by `configs_roles_examples_match_their_role`.

### Fixed

- `pqc-light-client` / `pqc-keystore`: the extracted crates opt into the workspace lints (their origins, `pqc-consensus` and `pqcd::wallet`, never did), so `cargo clippy -D warnings` surfaced 17 `indexing_slicing` / `expect_used` sites. All fixed without behaviour change: committee selection sorts and walks the validator set through iterators instead of raw indexing, CBOR signature pairs are destructured with `<[Value; 2]>::try_from`, BIP39 seed derivation uses the infallible `pbkdf2_hmac_array`, the HMAC-SHAKE key padding zips instead of slicing; the one unreachable `expect` (ciborium writing into a `Vec`) lives in a single documented helper. Test modules carry the workspace's usual `#![allow(clippy::unwrap_used, clippy::expect_used, clippy::indexing_slicing)]`. Direct `hmac` dependency dropped from `pqc-keystore`.
- `pqcd` doctest `cold_storage::upload_to_s3`: the `cargo build --features s3-upload` hint in the doc comment was an indented block, which rustdoc compiles as Rust; it only surfaced under `--all-features` (the CI test job never ran). Now a `text` fence.
- `crates/pqcd/tests/malicious_node.rs` — `invalid_parent_hash_blocks_get_rejected`: under `attack-modes` the attacker (validator-1) corrupts its own tip, so its own `append_block_trusted` rejects the block it built (`PARENT_HASH_MISMATCH`) and its consensus loop ends with an error; the test then failed on `shutdown()` although the property under test (honest majority keeps advancing) had passed. The attacker's join error is now reported, not propagated; the honest nodes must still shut down cleanly. The `malicious_node` binary gets `required-features = ["attack-modes"]`: without the feature no fault is injected and every scenario was vacuously green, which is how TASK-219b saw it pass in April.
- First full `cargo test --workspace --all-features` on record: 935 passed, 8 ignored; the three failures were the two above plus the load-sensitive `external_validator_registers_and_participates_in_quorum` (passes alone, TASK-239).
- `pqcd::tls`: the `tracing` import is now gated on `hybrid-kem-tls`, the only feature that uses it (was the single warning in a clean `cargo check --workspace --all-targets`).
