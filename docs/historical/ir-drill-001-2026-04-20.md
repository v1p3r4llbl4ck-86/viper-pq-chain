## Findings

### What worked
- Automatic checkpoint recovery: producer restarted cleanly from last checkpoint, no data loss, no manual state intervention needed.
- Automatic KEM re-establishment: followers re-connected within one sync tick after producer came back online.
- systemd restart path: `systemctl start pqcd` is sufficient — no config reload, no state wipe needed.
- No blocks were lost: height gap covered in seconds after producer restart.

### Gaps identified
- **G-001**: `sync_errors_total` counter does not reset on session recovery — it is a monotonic counter accumulating all errors since node start. During a real incident, this makes it hard to tell if errors are ongoing or historical. Mitigation: use the **rate** (`pqchain_peer_sync_errors_total[1m]`) in Zabbix/Prometheus, not the raw counter.
- **G-002**: Followers have no `/v1/metrics` endpoint — only `/internal/metrics` on the P2P port. The RUNBOOK §17 Prometheus scrape example lists `:26657` for all nodes, but follower ports are 26666/26676. Update scrape config accordingly.
- **G-003**: Service name is `pqcd.service`, not `pqchain-producer.service` as referenced in RUNBOOK §17 IR-01 remediation step A. RUNBOOK updated below.
